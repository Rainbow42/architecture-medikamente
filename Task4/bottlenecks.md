# Узкие места миграции

[Диаграмма Исикавы](ishikawa.drawio) и её [просмотр](ishikawa.svg) показывают причины риска: «Новая система не выдерживает рост 5× или выдаёт несогласованные данные». Это гипотезы на основе условия, а не результаты нагрузочного теста.

| Категория | Причина | Как проверить | Мера / приоритет |
|---|---|---|---|
| Инфраструктура | Один сервер обслуживает AD, Exchange, файлы и 1С; общие диск и отказ | IOPS, CPU, RAM, время backup в час пик; тест восстановления | Разделить роли и backup; резервирование до пилота. P0 |
| Данные | Дубликаты пациентов, разные форматы дат, потерянные связи сканов | Полнота обязательных полей, число конфликтов ID, сверка количества и контрольных сумм | Единый реестр, карантин, ручная сверка медработником. Не сливать только по ФИО. P0 |
| Интеграции | Файловая 1С/OLE, повтор платежа, недоступная лаборатория | Лаг, повторы, таймауты, расхождения сумм/статусов | Адаптер, durable outbox, idempotency, очередь с лимитом, reconciliation. P0 |
| ПО | Конкурентная запись на один слот, N+1 запросы, синхронный OCR | Два одновременных бронирования, p95/p99, план SQL, queue age | Unique constraint/транзакция; индексы; вынести OCR из OLTP. P0 |
| Люди | Три IT-специалиста и ручные процессы; нехватка компетенций ИБ/данных/тестирования | Карта ответственности, репетиция, время решения неоднозначной записи | Добавить backend, QA, data engineer и ИБ; обучить пользователей. P0 |
| Процессы | Неясный владелец данных, ручная двойная запись, нет критериев переключения | Кто утверждает расхождение; доля ручных исправлений; runbook drill | Один источник записи на фазу, явный go/no-go, журнал миграции. P0 |
| Безопасность | Массовый доступ к картам, тегирование после публикации, общие учётки | Негативные тесты и запрет чтения UNKNOWN, проверка аудита | Закрытый ingress, MFA, ABAC, separate runtime roles. P0 |
| Наблюдаемость | Нет базовой линии и метрик бизнес-операций | Сверить tracing с фактической операцией и доставку алерта | Метрики до миграции и dashboard пилота. P1, до cutover |

## Порядок действий

1. Закрыть общий доступ и подготовить восстановление; определить источники истины и владельцев.
2. Снять исходный профиль нагрузки и качества данных. Факт «рост 5×» без абсолютного QPS и размера файлов не позволяет рассчитать оборудование.
3. Проверить миграционный конвейер на копии синтетических/разрешённых обезличенных данных; отдельно проверить неверные кодировки, PDF без текста, дубликаты и большие файлы.
4. Прогнать 5× измеренный пик, всплеск 10× на коротком интервале, длительный прогон, отказ внешнего API и восстановление. Порог всплеска — тестовая гипотеза, не требование задания.
5. Провести пилот одного филиала/смены, измерить время записи пациента и число ручных исправлений.
6. Переключать только при выполнении критериев [cutover-плана](../Task5/cutover.md).

Считать нужно не только CPU: p95 записи/поиска, ошибки записи, конфликты слотов, число необработанных событий и возраст старейшего, пропущенные/дублированные платежи, задержку доставки результата, долю ложных классификаций. Для команды — lead time от принятой задачи до production, частоту релизов, долю неудачных изменений и время восстановления. Метрики служат поиску причин, а не рейтингу сотрудников.

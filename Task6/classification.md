# Классификация перед загрузкой

[Диаграмма C2](classification.drawio) и [просмотр](classification.svg) описывают самостоятельную подсистему подготовки аналитических данных. Здесь нет прямого пути из общего диска или источника в BI. Загрузчик принимает необработанные файлы только в закрытую landing-зону; публикация в аналитическое хранилище начинается после классификации и решения политики.

## Как проходит пакет

1. NiFi забирает разрешённую выгрузку или файл через TLS, проверяет источник, размер, хеш и формат. Записывает manifest: batch ID, source ID/version, schema fingerprint, цель, owner, время приёма, checksum. Неизвестный источник отклоняется. Чувствительное содержимое не кладётся в атрибуты NiFi, журнал или каталог.
2. Файлы попадают в encrypted landing bucket без прав BI. Парсеры обрабатывают Excel, CSV, JSON и сканы. Учитываются скрытые листы, примечания и метаданные; макросы не выполняются. Локальный OCR и антивирус работают в изолированных workers с ограничением CPU/RAM/времени и без внешней сети. Вложенный архив/повреждённый файл/неподдерживаемый формат отправляется в карантин, а не пропускается как безопасный.
3. Schema profiler сравнивает fingerprint с реестром: новые/удалённые поля, смена типа, вложенные объекты. При изменении заново проверяется весь затронутый набор. Старое одобрение не переносится автоматически на новую схему.
4. Классификатор сочетает словарь названий, regex/checksum-правила, локальный NER для русскоязычных ФИО/контактов/медицинского текста и контекст источника. Вход из клинического домена сохраняет MEDICAL даже при отсутствии найденного диагноза. Проверяется весь пакет, а не только случайные первые строки.
5. Policy service получает теги, confidence, версию схемы/правил и цель. UNKNOWN, конфликт правил или confidence ниже согласованного порога отправляют пакет в карантин. Порог задаётся отдельно по классу после размеченного теста; «0,9» нельзя выдавать за универсальную гарантию. При недоступном policy service публикация запрещена.
6. Steward просматривает ограниченный образец в защищённом рабочем месте. Исправление метки и причина версионируются; понижение MEDICAL/PII требует второго согласующего. Правка правила запускает повторную проверку затронутых наборов. Экспорт образцов из каталога запрещён.
7. Transform worker удаляет лишние поля, токенизирует идентификаторы, обобщает даты/редкие признаки по цели. Token vault отделён от аналитиков и базы curated, доступ только этому worker. После трансформации выполняется повторный поиск PII и проверка связей/агрегатов.
8. Publisher записывает immutable dataset version, сверяет количество/hash, затем атомарно публикует approved manifest. Только он имеет права записи в curated/marts. Сбой оставляет непубличную версию; retry с тем же batch+schema+policy не дублирует данные. Права на объекты не выдаются по одному лишь пользовательскому тегу.
9. OpenMetadata получает схемы, классы, владельца, policy ID и lineage source → transform version → dataset → витрина/модель. Payload и секреты не передаются. Retention worker отслеживает производные наборы, отзыв цели и удаления.

## Слои и доступ

| Слой | Содержимое | Доступ и защита |
|---|---|---|
| Landing / quarantine | Исходные неразмеченные файлы и отклонённые пакеты | Только ingestion/workers и назначенный steward; KMS, изоляция сети, короткий TTL; это не общедоступное «озеро» |
| Restricted raw | Принятый оригинал, если хранение нужно для конкретной цели | MEDICAL/PII сохраняются; владелец и отдельные ключи, нет прямого BI/ML; не бессрочная копия |
| Curated | Нормализованные, проверенные и псевдонимизированные записи | Сохраняет конфиденциальный статус; row/column policies и purpose-bound grants |
| Marts | Агрегаты для конкретного отчёта | Минимальный набор, подавление малых групп, лимиты экспорта и защита от разностных запросов |
| ML dataset registry | Одобренные версии обучающих/оценочных наборов | Отдельное назначение, lineage до модели, тест memorization/утечки; не использовать неразмеченные карты для LLM |

Отзыв основания запускает поиск зависимых наборов и их блокировку/пересборку. Для уже обученной модели удаление строки из исходного файла недостаточно: владелец оценивает необходимость вывода модели и переобучения, до решения выдача этой модели ограничивается. Обязательное хранение первичного меддокумента не даёт автоматического права обучать на нём модель.

## Метрики и качество

До выпуска нужен размеченный контрольный набор с разными форматами, OCR-ошибками, скрытыми полями и новыми схемами. Реальные данные без разрешения в этот набор не включаются.

| Метрика | Расчёт и применение |
|---|---|
| Recall по PII и MEDICAL | TP / (TP + FN), отдельно по классу, источнику и формату; пропуск медицинских данных опаснее лишнего карантина |
| Precision по классу | TP / (TP + FP); помогает уменьшать ручную нагрузку, не ослабляя критичные правила |
| False negative rate | FN / (TP + FN); release gate на контрольном наборе, разбор каждого критичного пропуска |
| Покрытие | Доля полей и файлов с решением политики; для публикации 100%, UNKNOWN = 0 |
| Drift | Доля новых fingerprints и сдвиг распределений; рост вызывает review источника/правил |
| Quarantine rate и возраст | Заблокированные пакеты / все пакеты; p95 времени решения и число просроченных |
| Пропускная способность | Файлы/с, строки/с, байты/с; отдельно OCR и структурированные файлы |
| End-to-end lag | От приёма до approved manifest; p95, возраст очереди и время ожидания steward |
| Качество публикации | Дубликаты batch ID, расхождения количества/hash и частичные версии; ожидается 0 |
| Утечка после преобразования | Найденные прямые идентификаторы в публикуемом наборе; блокирует релиз и выдачу |

Проектный стартовый критерий: recall ≥ 99,5% для PII/MEDICAL на репрезентативном наборе и 0 критичных пропусков на обязательных негативных кейсах. Это цель, не измеренный результат и не гарантия безопасности. На малом наборе процент недостоверен: указываются размер выборки, число ошибок и доверительный интервал. Нельзя компенсировать низкий recall быстрым конвейером.

## Рост 5×

Workers stateless, задачи партиционируются по batch ID; результат и контрольная точка находятся во внешнем хранилище. OCR масштабируется отдельно от лёгких парсеров. Очередь ограничена по байтам и количеству, backpressure останавливает приём/просит источник повторить позже. Переполнение не означает потерю или обход классификации.

Пакеты обрабатываются потоково, большой файл делится на части с общим manifest; публикация только после проверки всех частей. Лимиты по источникам не дают одному филиалу вытеснить остальные. Сервис записи пациентов не использует эту очередь синхронно, поэтому тяжёлый импорт не блокирует приём.

Проверяется 5× фактический суточный объём и пик, включая долю сканов. Масштабировать надо также каталог, KMS, token vault, объём очереди и работу steward: добавление CPU не исправит недельный backlog ручного согласования. Сбой worker повторяет задачу, сбой политики закрывает публикацию, сбой каталога удерживает manifest до фиксации обязательного lineage.

OpenMetadata помогает хранить классификацию, но стандартное распознавание PII не покрывает автоматически все русскоязычные медицинские форматы. Поэтому локальные распознаватели и их контрольный набор — отдельная часть реализации. Самих детекторов и production-конвейера это архитектурное задание не требует; на диаграмме они показаны как проектируемые контейнеры.

# Архитектура «Медикаменте»

Выбрала модульное приложение на Java и PostgreSQL для операционной части. Для трёх IT-специалистов полноценная микросервисная платформа, Kafka и Kubernetes одновременно с миграцией были бы слишком большой нагрузкой. Границы доменов при этом задаются сразу, чтобы их можно было выделять независимо позже.

[Редактируемая C4-схема](architecture.drawio) содержит три страницы: [контекст MVP](context-mvp.svg), [целевой контекст](context-target.svg) и [контейнеры](containers.svg). Контекст не смешивает таблицы БД с внешними системами. На контейнерной схеме показаны новые блоки безопасности и аналитики.

## MVP — первые восемь недель

Портал пациента и рабочее место ресепшена используют один сервис записи. У слота уникальная комбинация специалиста и времени, бронирование выполняется транзакционно; повтор запроса с тем же idempotency key возвращает прежний результат. Источник истины о записи — PostgreSQL, Excel после переключения доступен только для чтения.

MVP включает реестр пациента, контакты, договор/основания обработки, расписание, создание и отмену записи, список на следующий день для ресепшена и специалиста. Ресепшен связывается с пациентом за день до приёма; задачи напоминаний видны и отмечаются выполненными. Контакт передаётся только этому процессу, диагноз в напоминание не включается.

Начальную привязку ЛК к существующей карте подтверждает ресепшен по принятой процедуре идентификации. Совпадение телефона или ФИО само по себе не даёт доступа к карте. Дубликаты и представители несовершеннолетних требуют отдельной проверки; пациенту нельзя передать `patient_id` другого человека в запросе.

Медкарты в MVP остаются в выделенном защищённом архиве с доступом только медицинских работников. 1С и ККМ сохраняются: переписывать расчёт зарплаты и фискальный учёт в первом релизе не требуется. Аналитический слой сначала принимает контролируемые выгрузки записи и платежей; медицинские наборы не публикуются до проверки классификации.

## Целевое состояние — до двенадцати месяцев

Добавляются медицинская карта, лабораторный адаптер, платёжный шлюз, мобильный ЛК, push/голосовые напоминания и аналитические витрины. Уведомление содержит минимум сведений и ссылку на ЛК; диагнозы и анализы не читаются голосовым роботом. Подтверждение или отмена меняют единую запись и создают задачу/событие для ресепшена. Transactional outbox и повторяемый потребитель защищают от потери и дублирования уведомлений.

Домены разделены по назначению: Patient Registry — идентификация и контакты; Scheduling — слоты и записи; Clinical — медкарта и анализы; Billing — счета и статусы платежей; Workforce — кадры в 1С; Inventory — ТМЦ в 1С. Модули не читают чужие таблицы напрямую. Адаптеры 1С выполняют согласованный обмен, не дают внешним клиентам доступ к файловой базе или OLE.

Провайдер оплаты принимает карточные реквизиты на своей странице. В клинике остаются payment ID, сумма, назначение и статус; PAN/CVV не сохраняются. Подписанный callback сверяется с ожидаемым заказом, повторы не создают новый платёж.

## Privacy by Design

| Принцип | Решение до реализации |
|---|---|
| Предупреждение риска | Модель угроз, реестр целей/оснований и негативные сценарии входят в design review API |
| Закрыто по умолчанию | Неизвестная роль, цель или тег дают deny; выгрузка не разрешена автоматически |
| Защита встроена | OIDC/MFA, policy enforcement в API, отдельный архив, KMS, аудит, retention worker |
| Функциональность | Ресепшен видит запись и контакт без диагноза; врач получает данные для лечения без доступа к зарплатам |
| Весь жизненный цикл | Сбор → хранение → экспорт → отзыв/удаление; контроль реплик и резервных копий |
| Прозрачность | ЛК показывает сведения и основания, позволяет подать запрос; операции доступны для аудита |
| Контроль пациента | Отдельные согласия на дополнительные цели; отказ от маркетинга не запрещает медицинскую помощь |

## Кто что видит

| Роль | Разрешено | Дополнительное условие |
|---|---|---|
| Пациент | Собственные записи, договоры, опубликованные заключения и анализы | Подтверждённая связь subject → patient ID; не брать владельца из параметра клиента |
| Ресепшен | Идентификация, контакт, договор, слот и статус приёма | Назначенный филиал; без диагноза и текста заключения |
| Врач | Карта, направления, результаты | Действующее назначение на лечение; доступ к своим пациентам, не ко всем картам филиала |
| Кассир | Счёт, сумма, платёж и ограниченные идентификационные сведения | Без медицинского содержания |
| Бухгалтер | Бухгалтерские и кадровые документы | Только служебная цель; медицинские данные не импортируются |
| Склад | Номенклатура, остатки, поставщики | Без данных пациентов |
| Аналитик | Утверждённые витрины | Без raw, таблицы токенизации и прямых идентификаторов |
| IT-администратор | Инфраструктура и технические метрики | Нет штатного чтения карт; временный привилегированный доступ с согласованием и аудитом |

В неотложном случае break-glass для врача требует причины, короткого срока и последующего контроля ответственным за ПДн. Это не постоянно включённая роль. Удалённые сотрудники используют VPN/ZTNA и MFA. PostgreSQL RLS — второй рубеж, не замена авторизации API: приложению не выдаётся superuser/BYPASSRLS, владелец таблиц отделён от runtime-роли.

## Лаборатория и будущие интеграции

API передаёт lab-order token, код исследования и только обязательные атрибуты пациента по договору с лабораторией. Полную карту выгружать нельзя. mTLS удостоверяет систему, OAuth scope — операцию; объектная проверка ограничивает обработку выданными направлениями. Результат сверяется с заказом, подписью, единицами и версией; неизвестный заказ уходит в карантин, не в карту случайного пациента.

Общий шаблон контрактов содержит allowlist полей, purpose, классификацию, срок хранения и политику авторизации. В CI проверяются OpenAPI, обязательность тегов, запрещённые поля, BOLA, повторные callback и журналирование. Это уменьшает повторную ручную работу, но не означает, что новую интеграцию вообще можно не проверять: изменение назначения или состава данных требует согласования владельца и ответственного за ПДн.

## Аналитика, эксплуатация и рост

Данные загружаются через закрытый шлюз классификации, а не напрямую из общего диска в ClickHouse. Restricted raw и quarantine недоступны BI/ML. Проверенные псевдонимизированные данные сохраняются в curated; для BI выделяются агрегированные витрины. Обучение ML/LLM разрешается только на утверждённом наборе для отдельной цели, без отправки медкарт во внешние общедоступные сервисы.

Целевые SLO для согласования с клиникой: 99,9% доступности записи, p95 создания записи ≤ 1 с при пятикратной пиковой нагрузке, RPO ≤ 5 минут, RTO ≤ 1 часа. Это проектные цели, не результаты измерений. До закупки нужно измерить исходные объёмы и пики, проверить 5× профиль и восстановление.

Все среды с ПДн, резервные копии, ключи и аудит размещаются в РФ. MVP — две VM приложения, PostgreSQL с резервированием, отдельное объектное хранилище и backup-площадка. Горизонтально масштабируются stateless API и классификаторы, вертикально/репликами — БД; аналитика изолирована от OLTP. Kubernetes рассматривается после появления эксплуатационной команды и подтверждённой необходимости.

Филиалы, роли, политики хранения, правила классификации и каналы уведомлений конфигурируются версионируемо, с проверкой и откатом. Их нельзя менять в обход согласования прав доступа. VictoriaMetrics получает задержки, ошибки, лаги и отказы политик; SIEM — аномалии доступа. Тела меддокументов в метрики и логи не передаются.
